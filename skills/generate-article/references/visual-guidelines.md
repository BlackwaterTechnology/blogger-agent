# 长文视觉与渲染规范

创作时在规划或制作图片前读取；审稿时在检查图片前读取。以下是项目内部设计默认值，不是微信公众号官方标准。用户指定风格优先，但仍要检查可读性与事实表达。

## 选择值得画的内容

一张图解决一个理解问题。机制图表达关系或步骤；截图证明实际界面或结果；数据图表达有来源的量化关系。装饰性插画仅在帮助建立场景时使用，不代替证据。正文无需配图时只交付封面。

### 6 大专业表现模式与信息拓扑分析

将软件工程与 UML 建模思维融入移动端信息设计，根据技术信息的本质关系，在制图前**充分分析并按需匹配**对应的表现模式。**严禁机械式地仅采用结构化纯文字色块卡片**（即把几段文字切碎塞进 3 个带颜色的矩形框里，缺少拓扑、状态或几何关系）：

| 表现模式 | UML / 软件工程映射 | 解决的认知痛点 | 适用技术场景与视觉特征 |
|---|---|---|---|
| **1. 便当盒网格 (Bento Spec)** | 类图 / 对象规约 | 静态参数离散、难以快速比对核心属性 | 实体规格、参数配比、多维能力总览。特征：紧凑网格、Pill 胶囊标签、Key-Value 键值对 |
| **2. 垂直时序管道 (Causal Pipeline)** | 活动图 / 顺序图 | 时序逻辑推演冗长、因果连锁不直观 | 故障传播链、多步执行链路、请求生命周期。特征：垂直 1➔2➔3➔4 递进、阶段状态色阶、驱动连线 |
| **3. 二元对抗/四象限 (Trade-off Matrix)** | 决策分支 / ATAM 权衡 | 选型纠结、难以洞察反模式代价 | 技术选型（c5a vs r5a）、新旧范式对比、2x2 成本/收益象限。特征：左右红绿双栏（✕ vs ✓）、决策分水岭 |
| **4. 系统拓扑边界 (Topology Map)** | 部署图 / 组件图 | 局部割裂、缺乏空间与容器边界感 | 架构全景、网络组网、容器包含关系（VPC > Subnet > Node > Pod）。特征：嵌套虚线框、节点连接线、总线流向 |
| **5. 状态机闭环 (State Machine)** | 状态机图 (Statechart) | 状态流转不清、异常处理与重试遗漏 | 控制循环（Reconcile）、探针检测、退避重试。特征：圆角状态节点、带守卫条件的转移箭头 [Guard]、回路 |
| **6. 实证量化/终端切片 (Trace & Benchmark)** | 性能画像 / 执行跟踪 | 纯理论推演缺乏实操证据与信服力 | 压测剪刀差折线图、基准测试柱状图、CLI 终端窗口切片。特征：真实终端三色按钮、Monospace 等宽代码高亮 |

*辅助增强模态：具象概念隐喻 (Conceptual Metaphor)*：对标 DDD 领域概念模型。用于封面爆破 Hook 或枯燥抽象概念降维（如用“天平倾斜”表达调度失衡）。环境具备且用户需要时通过 `generate_image` 生成去 AI 味的高审美社论插画。

关键解释保留在正文，图注说明读图重点；截图应裁去无关区域，并检查账号信息等私人内容。数据图标明单位、条件和来源，避免误导坐标轴；模拟数据或终端演示不能伪装成实测证据。不要为凑模态而混用多种画风。避免机械堆砌无拓扑关系的纯文字方块，让每张图发挥不可替代的空间/建模解释力。

### 禁绝 ASCII/Unicode 伪字符图表 (Zero ASCII Diagrams - CRITICAL)

- **严禁字符画伪装图表**：严禁在 Markdown 正文中使用 `┌─┐`、`│`、`└─┘`、`+---+`、`|---|` 等方框字符代码块替代真实图表。
- **移动端崩溃致命伤**：移动端视口仅 360px~390px 且等宽字体支持参差不齐，字符框图在手机端 100% 发生自动折行与错位撕裂，彻底沦为乱码线框。
- **真实资产交付闭环**：正文一旦出现“以 xxx 为例，来看一张典型的 xxx 是如何设计的”、“如下图所示”，**必须且只能紧随真实的图片 Markdown 语法 `![caption](image.png)`**，并在同级目录下实际生成高画质 PNG 与对应可编辑矢量源文件（SVG / 脚本）。
- **脚本动态路径**：目录下的绘图构建脚本必须使用 `Path(__file__).parent.resolve()`，严禁硬编码特定历史绝对路径。


## 手机尺寸验收

使用实际显示尺寸计算字号：`显示字号 = 源字号 × 显示宽度 / 源画布宽度`。提高 PNG 分辨率或 DPI 不会让同一布局里的文字变大。

- 以 360px 显示宽度为主要预览，核心文字目标约 16px 或更大，辅助文字不低于 14px；同时检查 320px 窄屏。读不清就减字、改单栏或拆图。
- 在 1200px 源画布中，对应核心文字约 54px，辅助文字至少 47px。标题按层级放大，不沿用旧模板中的 20–28px 小字。
- 截图、图表、图片内代码同样检查最终显示效果。无关的小字可以裁去；必要的小字应放大局部或改用正文解释，不能仅因 SVG 字号合格就通过验收。
- 不固定横纵比例或分栏数量。按信息关系选择画布，优先单栏；双栏只有在手机预览仍清楚时使用。长流程可以拆图，不以缩小文字容纳更多节点。
- 保留清晰对比和留白，颜色之外再用文字或形状区分类别。无须每图添加徽标、英文标签或总结横条。

保存至少 360px 与 320px 宽的预览，按原始尺寸查看，检查中文缺字、溢出、遮挡、箭头方向、图注与正文一致性。预览只证明本地视觉效果，不能代替微信后台实际排版验证。

## 封面

默认 `cover.png` 沿用现有工具的 16:9 输出，保留一个主要视觉重点。短标题或主题图均可，不强制双栏、微型数据卡片、4–8 字口号或特定配色。封面标题可以比文章标题短，但不能改变含义或夸大结论。

分别查看横图缩略图与中心方形裁切。方形裁切无需保留所有装饰，但主体与核心文字不能切断；失败时调整主体位置、缩短文字或删去次要元素。不要以“中央 60%”声称所有比例都安全：16:9 原图中心裁成正方形只保留原宽的 56.25%，裁成 3:4 只保留 42.19%。

3:4 图片消息按需单独设计，不为它牺牲长文配图。实际发布界面要求其他比例时按具体预览调整，不把 16:9 称为平台唯一要求。

## 工具选择与可用性

先检查当前系统、已安装工具和中文字体，不假定存在 `sips`、个人目录中的 JAR 或任何特定图片生成工具。复用已提供素材和已安装能力；缺少必要依赖时说明实际缺口，不用缺字图片或空文件冒充成品。

| 需求 | 优先路径与替代方式 |
|---|---|
| 简洁文字封面 | 仓库 `tools/generate_cover.py`；依赖 Pillow、loguru 和中文字体。现有字体回退偏向 macOS，其他系统需先试渲染；缺字时改用能指定中文字体的 SVG/浏览器渲染 |
| 精确机制图 / 信息图 | 手写 SVG，按手机字号设计；优先用可用的本地浏览器渲染为 PNG。CairoSVG 或已安装的本地矢量渲染器可作为替代，先验证字体与布局 |
| 数据图 | 可用的 Matplotlib 或原生 SVG，数据、单位与注释来自已核查材料 |
| 已有 Mermaid / PlantUML | 可用的本地渲染器；布局不合格时先精简或拆分，必要时改 SVG，不因风格偏好强制重绘 |
| 概念插画 | 用户需要且环境有图片生成能力时使用；选择与内容一致的画面，检查失真与伪文字，不依赖特定供应商或固定风格目录 |

本地 SVG 转 PNG 可用 Playwright 打开仅含该 SVG 的本地 HTML，设置与源画布一致的 viewport，对 SVG 元素截图。等待 `document.fonts.ready`，使用确实含中文字形的字体，检查图片实际加载状态后再导出。禁止把缺少字体的回退结果当作通过。

`sips` 仅在 macOS 且确认当前输入格式能成功转换时使用，不是必需依赖。涉及远程渲染或上传源文档时，先确认内容允许交给该服务；默认优先本地处理。

原生 SVG/代码图保留可编辑源文件，文章引用实际生成的 PNG。常规导出可使用 1200px 或更宽源图；高分辨率用于清晰度，移动端布局用于可读性，两者分别验收。

## 依据与效果边界

清晰、可扫描、客观的文本有通用网页阅读研究支持，不能直接推断公众号推荐机制或具体增长比例：[NN/g 阅读研究](https://www.nngroup.com/articles/how-users-read-on-the-web/)。必要信息也应提供文字表达，避免只存在于图中：[W3C 图片指导](https://www.w3.org/WAI/tutorials/images/)。上述字号是内部设计目标，不是这两份资料规定的通用门槛。
