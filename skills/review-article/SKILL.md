# Review Article

以技术读者能否理解、信任并使用文章为标准。默认直接修复目标文章；用户只要求评审时，仅报告问题和修改建议。保留作者意图与已指定的读者、语气和范围，不把不同文章改成同一模板。

## 1. 阅读上下文与核查

阅读完整 `article.md`、引用的资产、用户原始材料及可用来源。先确认文章解决什么问题、核心回答是什么、标题承诺是否兑现；不因缺少策划文档阻塞审稿。

| 维度 | 检查重点 |
|---|---|
| 读者价值 | 问题是否具体，开篇是否交代阅读收益，建议是否适用于目标读者 |
| 事实可追溯 | 关键结论是否有对应证据；链接是否支持相关断言；事实、经验、推断和示例是否分清 |
| 论证完整 | 是否从证据得到结论；是否省略必要前提、反例、成本或适用条件；对比条件是否一致 |
| 表达自然 | 是否存在空泛背景、术语堆叠、口号、重复总结或虚构第一人称经历；小标题是否准确 |
| 视觉可读与模式匹配 | 图是否有新增建模/解释价值（是否针对技术信息按需采用拓扑、时序、状态机、权衡矩阵或实证切片，严禁纯文字色块卡片堆砌）；正文是否存在 ASCII/Unicode 框图伪装图表；关键文字是否无需放大可读；正文能否表达核心结论 |

核查影响结论的 API、命令、版本、数字和时效性事实，优先使用一手来源。未查到的资料明确标记为未核实，不把“名字听起来真实”或“附有链接”当作验证完成。不要为了验证而执行有外部副作用的命令。

图片存在时读取 [共享视觉与渲染规范](../generate-article/references/visual-guidelines.md)，查看实际渲染结果及必要的源文件，按手机显示尺寸检查。只有源码检查时不能声称已通过视觉验收。若发现图片仅仅是将正文段落机械拆分为带颜色的纯文字矩形框、缺少几何空间、状态机或拓扑关系的无效配图，应建议重构为对应的专业表现模式或直接删除该图。同时严格扫描 Markdown 正文，检查是否存在使用 `┌─┐`、`│`、`└─┘`、`+---+` 等字符画代码块伪装图表；若存在，必须将其重绘为真实 SVG/PNG 资产并替换正文，未修复前不得通过。

## 2. 区分阻断问题与编辑建议

**阻断问题：** 会误导读者或妨碍交付的问题，例如虚构证据、影响结论的事实待核实、标题承诺失实、主论证不成立、关键图片无法阅读或与正文矛盾、必要图片缺失、元数据不合法、**正文中残留 ASCII/Unicode 方框字符画（如 `┌─┐`、`│`）伪装图表而未生成真实图片**。可通过删除不可靠断言、缩小结论或重绘真实图表修复，但不得偷偷改变作者核心立场；核心立场依赖缺失证据时请求材料并保持待核实状态。

**编辑建议：** 不影响事实与交付的改进，例如开篇过长、重复段落、可以删掉的装饰图、含义不清的小标题或更自然的措辞。优先处理明显收益高的修改，不为个人偏好无限重写。

不以第二人称、编号、正常标点、无原创造词、无争议互动、无正文配图或不满足固定图数判失败。不要求每节一个数字或项目名，不强加新旧对抗、独立画册、双栏封面或固定配色，不预测传播指标或给出缺少依据的百分制评分。

## 3. 修复并验证交付

先修事实与论证，再修文字，最后检查资产和格式。图片错误需修改图片并复核；改不了就说明，不能只改正文后宣称全篇已修复。删除无价值图片时移除对应正文引用，避免误删用户其他资产。

- 保留 `title/author/desc/collection/cover` 与相对图片路径；作者沿用原有署名。`desc` 非空且去除首尾空白后不超过 120 字符，不设 60 字符下限。解析器针对短摘要的旧警告不作为阻断问题。
- `collection` 必须属于根目录 `blogger.toml` 的 `[platforms.wechat.accounts.default].article_collections`；不属于时选语义合适的现有项。没有合适选项或配置不可用时报告阻断，不修改账号配置来通过检查。
- `cover` 和 Markdown 引用的本地图片实际存在、可以打开；默认文章不带 `type: photo`。独立图片消息应转交对应工作流，不在此强行改成长文。
- 列表与上下文用空行分隔，代码保留围栏与可复制内容，避免重复标题；简单箭头优先使用 `→` 等 Unicode。真正的数学表达按现有解析器能力检查，不一律删除 LaTeX。
- 可用时调用现有 `parse_markdown_payload` 检查临时副本的元数据、图片与 HTML 结果；注意数学预处理可能生成图片。不要通过调用发布器验证格式，不触碰已登录浏览器。

最多两轮“审查 → 修复 → 复核”。第二轮后仍有阻断问题就停止并列出所需材料或条件；只剩编辑建议时可结束。审稿者不再派发审稿子代理。

## 4. 报告

向用户或主叫方给出简短报告：

- 状态：通过 / 待补材料或修复；只做评审时明确未修改文件。
- 影响最大的发现及已做的修改，指向相关段落或资产。
- 实际完成的事实核查、解析检查与视觉预览；没有执行的检查明确说明。
- 仍存在的阻断问题与必要的后续动作；可选建议与之分开。

“通过”仅表示在已说明的检查范围内未发现阻断问题，不代表事实绝对无误、平台审核通过或传播表现保证。报告留在对话中，不写进发布正文，不执行发布。
