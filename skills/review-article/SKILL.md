# Review Article Skill

## Overview

本 skill 担任文章草案的**终审官 (Chief Verification Officer / Evaluator)**。基于第一性原理与 **T-A-O 认知协作架构**，它对目标 `article.md` 进行百分制品控审查，彻底扫除 AI 腔陈词滥调、修复排版缺陷、核查真实性与视觉截断问题，并直接修改文件。

---

## 质量审核四大维度（百分制打分卡）

审核者必须按照以下 100 分制标准评估并修正草案：

```
                      ┌─────────────────────────────────────────┐
                      │        文章质量百分制打分卡 (100分)       │
                      └────────────────────┬────────────────────┘
                                           │
        ┌──────────────────┬───────────────┴──────────────┬──────────────────┐
        ▼                  ▼                              ▼                  ▼
 【1. 认知与论点】30分   【2. 文本与质感】25分          【3. 视觉与认知密度】25分 【4. 传播与合规】20分
 · 一句话主张 (10)      · 消除说教代词 (8)             · 2-4张高清结构图 (10)    · 标题冲突张力 (8)
 · 2+项硬核证据 (10)    · 开门见山直击痛点 (8)          · 图文紧密显式引用 (8)    · desc 60-120字 (6)
 · 命名实体/货币 (10)   · 剔除 AI 腔与废话 (9)          · 黄金扁平比无截断 (7)    · 0 真实性幻觉 (6)
```

### 打分标准与评级阈值
- **S 级（90 ~ 100 分）**：直接通过，可进行平台推送。
- **A 级（80 ~ 89 分）**：在审阅环节修润文字、标题与图注后通过。
- **B 级（70 ~ 79 分）**：打回要求补充案例证据或结构图表。
- **C 级（< 70 分）**：废弃重构，主张不明确或存在幻觉风险。

## Workflow

### 阶段 1：发布前自审 (Pre-flight Rubric Audit)

读取目标 `article.md` 文件，对照百分制标准**直接修改文件**修复问题：

```text
【发布前 Pre-flight 检查清单】
1. 极化主张与标题：标题是否具备反直觉张力？若为平铺直叙的话题陈述，必须改写。
2. 社交货币与命名实体：文中是否有明确提炼的方法论或概念实体（如 T-A-O 架构、审核权倒置悖论）？若没有，必须归纳提炼。
3. 人称排查（一票否决）：全局搜索“你/你的/您/您的”。除了引用对话预案外，正文叙述中绝不能出现第二人称代词！统一改写为“我们/大家/自身/开发者”或省略。
4. 开篇检查：第一句话能否让人停止滚动？若为“在……快速发展的今天”或“近期迎来重磅消息”，必须重写为具体场景或工程痛点开篇。
5. 证据硬度：每个小节是否包含至少 1 处硬核证据（具体代码、真实判例、项目名称、对比数字）？无证据的段落必须补充证据或删除。
6. 配图数量与孤儿图：正文必须包含 2~4 张高清结构图表（封面除外）。每张图必须在上下文中被显式引用（`![图注：...](...png)`）并解析。
7. 视觉截断检查：用 view_file 或 Read 工具检查 PNG 视觉资产。若 PlantUML 图片右侧或底部出现截断/文字裁切，必须将其重新绘制为 SVG 横向泳道（viewBox="0 0 1600 900"）并用 sips 转换覆盖。
8. 摘要长度：`desc` 实际字符数严格落在 60–120 字符范围内。
9. 0 真实性幻觉：核对文中所有 API 参数、法律判例、历史年份与项目名称，确保 100% 真实准确。
```

---

### 阶段 2：AI 腔急救包替换

扫描正文，若发现以下高危陈词，**写出即重写**：

| ✗ 写出即重写 | ✓ 替换方向 |
|------|------|
| "你 / 你的 / 您 / 您的" (正文叙述中) | 改写为 "我们 / 大家 / 自身 / 开发者"，或直接省略人称 |
| "在……快速演进/蓬勃发展的今天" | 替换为具体的工程痛点、场景或实验数据开篇 |
| "我们不禁要思考" / "值得深思" | 直接抛出具体问题或矛盾冲突 |
| "标志着 X 进入了一个全新的阶段" | 说清具体改变了什么旧结论或指标 |
| "必将迎来更令人惊叹的进化" / "在 X 滋养下成长" | 删掉，或换成可证伪的预测 |
| "在这样的多重夹击下" / "巨头纷纷下场" | 列出具体公司及他们做了什么 |
| "无疑会对 X 产生积极的促进作用" | 替换为具体的效率提升百分比或量化对价 |
| 段落收尾："未来可期 / 拭目以待 / 让我们一同见证" | 直接结束。中文写作不需要总结的总结 |
| 生硬的小标题数字编号（`### 1. 核心背景`） | 改写为自然流畅的结构短语（如 `### 核心背景与工程瓶颈`） |

---

### 阶段 3：格式微调

- **列表空行**：确保 `- ` 列表或数字列表前**必须有空行**，避免 Markdown 渲染黏连。
- **总结大标题**：避免使用“### 总结”作为最终大标题，改用有实质认知价值的归纳小标题（如 `### 认知回归：掌控智能时代的终审权`）。

---

### 阶段 4：报告审阅结果

完成修改后，向主叫方回复审阅报告，列出：
1. 百分制打分卡得分及评级（S / A / B）。
2. 修改的具体点（如去除了哪些第二人称代词、消除了哪些 AI 腔、修润的 `desc` 长度、修复的图表等）。
